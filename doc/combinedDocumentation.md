```markdown
# AIAssistant::Application

Abstract base class defining an AI assistant application's lifecycle and event interface.

- `virtual void OnShutdown() = 0;`

## Usage

Subclass `AIAssistant::Application` and implement all pure virtual methods. Lifecycle:

1. `OnStart()`
2. Repeatedly: `OnUpdate()` and `OnEvent(...)`
```

# FileCategorizer Class Documentation

Namespace: `AIAssistant`

---

## Overview

`FileCategorizer` categorizes and tracks files relevant to the AI assistant system. It assigns files to categories such as Settings, Context, Tasks, Requirements, Subfolders, or Ignored, maintains tracking state, and handles file additions, removals, and modifications. It applies file naming rules, file content heuristics, and size limits to determine relevance and category.

---

## Related Types

- **FileCategory**: Enum representing file types (`Settings`, `Context`, `Task`, `Requirement`, `SubFolder`, `Ignored`).
- **TrackedFile**: Metadata and state for a monitored file.
- **TrackedFiles**: Container mapping file paths to `TrackedFile` instances within one category, tracks modification counts and dirty state.
- **CategorizedFiles**: Aggregates all `TrackedFiles` for each category.

---

## Public Methods

### `fs::path const AddFile(fs::path const& filePath)`

- Categorizes and adds a new file to tracking.
- Creates a `TrackedFile` and inserts it into the category’s map.
- Marks category dirty and increments modified files count.
- Returns the input `filePath`.

### `fs::path const RemoveFile(fs::path const& filePath)`

- Removes the file from all categories if tracked.
- Updates modified count and dirty flag appropriately.
- Returns the input `filePath`.

### `fs::path const ModifyFile(fs::path const& filePath)`

- Re-categorizes and updates tracking of an existing file.
- If content has changed and file was unmodified, marks as modified and increments counter.
- Ignores if file is categorized as ignored or not tracked.
- Returns the input path; returns empty path if ignored.

### `CategorizedFiles& GetCategorizedFiles()`

- Provides access to all tracked files grouped by category.

### `void PrintCategorizedFiles() const`

- Prints tracked files organized by categories to standard output.

---

## Private Methods

### `FileCategory Categorize(fs::path const& filePath) const`

- Assigns a category based on:
  - Directory status
  - File name prefixes (`STNG`, `CNTX`, `TASK`)
  - PROB file pattern and timestamps (ignores stale files)
  - Binary format detection (magic numbers for ZIP, PDF, images, executables)
  - Text content heuristics (non-printable character ratio)
  - File size limits (creates `.output.txt` message for oversized files)
- Returns the determined `FileCategory`.

### `void RemoveFromFiles(TrackedFiles& files, fs::path const& path)`

- Removes a file from a specific category container.
- Adjusts modified count if necessary and marks container dirty.
- Logs removal event.

---

## Data Members

- `CategorizedFiles m_CategorizedFiles` — stores tracked files across categories.

---

## Behavior Notes

- Files deemed binary, unreadable, empty, stale, or oversized are categorized as `Ignored`.
- Modification tracking increments only if file contents changed.
- File categorization optimizes downstream AI processing by ignoring irrelevant files early.
- Logging traces ignored files, file removals, and modifications.

---

## Usage Example

```cpp
AIAssistant::FileCategorizer categorizer;
std::filesystem::path file("TASK_example.txt");

categorizer.AddFile(file);
categorizer.ModifyFile(file);
categorizer.RemoveFile(file);
categorizer.PrintCategorizedFiles();
```

---

## Summary

`FileCategorizer` automates classification and modification tracking of AI assistant files, filtering out irrelevant or problematic files, supporting efficient file management and integration within the application.

# AIAssistant::ProbUtils

Namespace providing utilities to parse and validate PROB problem filenames.

## struct ProbFileInfo

Stores information extracted from a PROB filename.

| Member      | Type      | Description                                  |
|-------------|-----------|----------------------------------------------|
| `id`        | `uint64_t`| Numeric problem identifier from the filename |
| `timestamp` | `int64_t` | Timestamp extracted from the filename        |
| `isOutput`  | `bool`    | `true` if an output file (`.output.txt`), `false` if input (`.txt`) |

---

## Functions

### `std::optional<ProbFileInfo> ParseProbFilename(std::string const& filename)`

Extracts problem metadata from a filename matching the format:

- Starts with `"PROB_"`.
- Ends with either `".txt"` (input) or `".output.txt"` (output).
- Pattern: `PROB_<id>_<timestamp>.txt` or `PROB_<id>_<timestamp>.output.txt`.
- `<id>` is a positive integer.
- `<timestamp>` is a signed integer.

Returns:

- `ProbFileInfo` with parsed fields on success.
- `std::nullopt` if format is invalid or parsing fails.

---

### `inline bool IsProbFile(std::string const& filename)`

Returns `true` if `filename` is a valid PROB file according to `ParseProbFilename`, otherwise `false`.

---

## Example

```cpp
auto result = AIAssistant::ProbUtils::ParseProbFilename("PROB_42_1680000000.output.txt");
if (result)
{
    auto info = *result;
    // info.id == 42
    // info.timestamp == 1680000000
    // info.isOutput == true
}
```

---

## Summary

`ProbUtils` enables quick validation and parsing of problem file names formatted as PROB files, extracting ID, timestamp, and input/output status, facilitating both human and AI usage.

# Class `JarvisAgent`

`JarvisAgent` is the main application class in the `AIAssistant` namespace responsible for managing the lifecycle and coordination of subsystems in an AI assistant platform. It inherits from `Application` and integrates components such as workflow orchestration, scripting, web server, file watcher, AI request handling, and session management.

---

## Overview

This class implements core functions to start, update, handle events, and shut down the application. It orchestrates workflows, task executors, triggers, and manages interactions between AI requests, chat messages, file-based triggers, and the embedded Python engine.

---

## Key Responsibilities

- **OnStart()**  
  Initializes and starts:
  - Internal task registry with built-in tasks (e.g., `CarMaintenanceTask`)
  - Terminal status renderer hooks
  - File watcher on configured folder
  - Web server HTTP interface
  - Python scripting engine
  - AI request pool
  - Workflow registry and validation
  - Task executors for Shell, AI calls, Python, Internal tasks
  - Workflow runtime manager and trigger engine, binding triggers

- **OnUpdate()**  
  Periodic update tasks:
  - Updates all session managers
  - Cleans expired chat messages
  - Periodically broadcasts Python engine status to web clients
  - Updates AI requests, workflow runtime, trigger engine
  - Checks if app should terminate

- **OnEvent(std::shared_ptr<Event>&)**  
  Handles incoming events by dispatching:
  - Engine shutdown events
  - File system events (added/modified/removed), notifying triggers with startup suppressions
  - Python crash event (stops Python engine)
  - Handles AI call completion via PROB file detection, forwarding results to chat pool
  - Routes other file events to proper session managers
  - Forwards all events to Python engine

- **OnShutdown()**  
  Stops and cleans up:
  - Workflow runtime manager
  - AI request pool
  - Python engine and broadcasts status
  - File watcher and web server
  - All session managers

# TaskFreshnessChecker

`TaskFreshnessChecker` determines if a workflow task is up to date by comparing file timestamps of the task’s outputs against its inputs and upstream dependencies.

---

## Overview

Checks if a task’s outputs are fresh following these rules:
- All declared output files exist.
- The oldest output file’s timestamp is at least as recent as the newest input or upstream output.
- Inputs include the task’s declared inputs plus all outputs of its dependencies (transitive).

---

## Public Interface

### Struct: `ResolvedPaths`

Holds resolved file paths for a task:
```cpp
struct ResolvedPaths
{
    std::vector<std::filesystem::path> m_InputPaths;   // input file paths
    std::vector<std::filesystem::path> m_OutputPaths;  // output file paths
};
```

### Type: `ResolveOutputPathsFn`

Callable to resolve outputs for a given task ID:
```cpp
using ResolveOutputPathsFn = std::function<
    bool(std::string const& taskId, std::vector<std::filesystem::path>& outPaths)
>;
```
Returns `true` if output paths for `taskId` were successfully resolved.

### Method: `IsTaskUpToDate`

```cpp
bool IsTaskUpToDate(
    WorkflowDefinition const& workflowDefinition,
    std::string const& taskId,
    ResolvedPaths const& resolvedPaths,
    ResolveOutputPathsFn const& resolveOutputPaths
) const;
```

Returns `true` if all outputs exist and are not older than any input or upstream output. Returns `false` otherwise, or if any input or output is missing/unreadable.

---

## Internal Method

### `CollectUpstreamOutputTimes`

```cpp
bool CollectUpstreamOutputTimes(
    WorkflowDefinition const& workflowDefinition,
    std::string const& taskId,
    std::unordered_set<std::string>& visitedTasks,
    std::vector<std::filesystem::file_time_type>& outTimes,
    ResolveOutputPathsFn const& resolveOutputPaths
) const;
```

Recursively collects modification times of all outputs from `taskId` and its dependencies. Tracks visited tasks to avoid cycles. Returns `false` if any output is missing or unreadable.

---

## Behavior Notes

- Tasks with no outputs are always considered out of date.
- If neither inputs nor upstream outputs exist, freshness cannot be confirmed.
- Path normalization using `lexically_normal()` is applied before existence and timestamp checks.
- Utilizes C++17 `<filesystem>` APIs.
- Prevents infinite recursion in dependency graph traversal.

---

## Namespace

All declarations are contained in the `AIAssistant` namespace.

---

## Summary

`TaskFreshnessChecker` supports efficient incremental workflows by verifying task freshness based on file timestamps of the task’s inputs, outputs, and the outputs of all upstream dependencies.

# TriggerEngine Class Documentation

Namespace: `AIAssistant`

---

## Overview

`TriggerEngine` manages registration and firing of various workflow triggers. It:

- Evaluates cron expressions on periodic ticks.
- Responds to file system events.
- Handles manual trigger invocations.

It does **not** parse workflow JSON; that is done elsewhere.

---

## Responsibilities

- Register triggers of types: auto, cron, file-watch, manual.
- Fire triggers through a user-provided callback.
- Track trigger enabled state.
- Manage file-trigger lookup with path normalization and debouncing.
- Clear triggers for workflows on reload.

---

## Public API

### Enum: `FileEventType`

- `Created`
- `Modified`
- `Deleted`

---

### Struct: `TriggerFiredEvent`

- `std::string m_WorkflowId` — workflow identifier.

---

### Type: `TriggerCallback`

Function signature: `void(TriggerFiredEvent const&)`  
Called when a trigger fires.

---

---

```cpp
void AddAutoTrigger(std::string const& workflowId, std::string const& triggerId, bool isEnabled);
```

- Fires once immediately if enabled.

```cpp
void AddCronTrigger(std::string const& workflowId, std::string const& triggerId, std::string const& expression, bool isEnabled);
```
- Adds a cron trigger with a 5-field cron string (minute hour day month weekday).
- Enabled triggers are evaluated on `Tick()`.

```cpp
void AddFileWatchTrigger(std::string const& workflowId, std::string const& triggerId, std::string const& path, std::vector<FileEventType> const& events, uint32_t debounceMilliseconds, bool isEnabled);
```
- Adds a file-watch trigger on given path and events.
- Includes debounce interval to limit re-firing.

```cpp
void AddManualTrigger(std::string const& workflowId, std::string const& triggerId, bool isEnabled);
```
- Adds a manual trigger, fired only explicitly.

```cpp
void ClearWorkflowTriggers(std::string const& workflowId);
```
- Removes all triggers related to a workflow.

---

### Runtime Methods

```cpp
void Tick(std::chrono::system_clock::time_point const& now);
```
- Evaluate and fire due cron triggers.

```cpp
void NotifyFileEvent(std::string const& path, FileEventType fileEventType, std::chrono::system_clock::time_point const& now);
```
- Process file event notifications.
- Fires matching file-watch triggers respecting debounce.

```cpp
void FireManualTrigger(std::string const& workflowId, std::string const& triggerId);
```

- Fires a registered manual trigger, if enabled.

---

## Internal Details

### `CronExpression`

- Parses minimal cron expressions with fields: minute, hour, day-of-month, month, day-of-week.
- Each field supports either `"*"` (wildcard) or an exact integer.
- Computes next fire time after a reference time, searching up to one year ahead.

### Trigger Instance Types

- `CronTriggerInstance`: stores workflow/trigger IDs, parsed cron expression, next fire time, enabled flag.
- `FileWatchTriggerInstance`: stores watched path (normalized), event types, debounce interval, last fire time, enable state.
- `ManualTriggerInstance`: stores workflow/trigger IDs and enabled flag.

### File-Watch Index

- Maps normalized paths to registered file watch triggers for quick lookup.
- Supports exact path matches and prefix matches (directory).

### Path Handling

- Paths normalized with forward slashes and duplicate slashes removed.
- Events match if exact path or event path prefixed by watched directory.

### Debouncing

- File triggers only fire if enough time elapsed since last fire, or first event.

---

## Usage Summary

1. Create `TriggerEngine` with a trigger-fired callback.
2. Register triggers with appropriate methods.
3. Call `Tick()` regularly to fire due cron triggers.
4. Forward file events via `NotifyFileEvent()`.
5. Fire manual triggers via `FireManualTrigger()`.
6. Clear triggers on workflow reload with `ClearWorkflowTriggers()`.

# WorkflowOrchestrator

`WorkflowOrchestrator` is a singleton C++ class that manages and executes workflows asynchronously without blocking the main thread. It schedules tasks considering their dependencies and freshness of input/output files, tracks workflow progress, and stores run states for inspection.

---

## Core Responsibilities

- Uses `WorkflowRegistry` for workflow definitions lookup.
- Starts and tracks ephemeral `WorkflowRun` instances.
- Checks task readiness based on dependencies (`depends_on`).
- Performs Makefile-style freshness checks on task input/output files.
- Dispatches task execution asynchronously on a thread pool.
- Progresses workflows via `Tick()`, never blocking main-thread event processing.
- Tracks and exposes last completed runs and active runs for querying or mutation.

---

## Public Interface

- `static WorkflowOrchestrator& Get()`: Returns singleton instance.
- `void SetRegistry(const WorkflowRegistry*)`: Sets workflow definition registry.
- `std::vector<std::string> GetWorkflowIds() const`: Gets all workflow IDs.
- `std::string StartWorkflowRun(const std::string& workflowId, const std::string& runId = "")`: Starts a workflow run asynchronously, returns run ID or empty on failure.

## Purpose

- Execute workflows composed of multiple interdependent tasks.

- Integrate AI-based task completions asynchronously.

## Public API

### Lifecycle Methods

- **Start()**  
  Enables workflow run processing.

- **Stop()**  
  Stops all processing, clears queues, cancels pending work, and resets state.

### Workflow Run Control

- **EnqueueWorkflowRun(const std::string& workflowId)**  
  Adds a workflow execution request by ID to the pending queue.

- **Update()**  
  Advances workflow execution: starts pending runs, dispatches ready tasks, handles completions, and applies AI results.

- **SetRegistry(const WorkflowRegistry\* workflowRegistry)**  
  Provides the registry to resolve workflow definitions.

- **TryGetLastRun(const std::string& workflowId, WorkflowRun& outRun) const**

## Key Concepts

- **WorkflowDefinition**: Immutable workflow metadata including task graph and settings.
- **WorkflowRun**: Mutable state of a workflow execution instance.
- **TaskDef**: Defines a single task properties and dependencies.
- **TaskInstanceState**: Tracks state of a task (Pending, Ready, Running, Succeeded, Failed, Skipped, WaitingExternal).

- **TaskExecutionResult**: Outcome of a task execution attempt.
- **AiRequestCompletion**: AI task completion event handled asynchronously.

1. **Start Pending Runs:**  
   Move workflows from pending queue to active runs after retrieving definitions.

2. **Harvest Task Completion:**  
   Check futures of running tasks; update task states accordingly.

3. **Fail Propagation:**  
   Mark all WaitingExternal tasks as failed if workflow has failed and no running tasks remain.

4. **Dispatch Ready Tasks:**  
   For tasks in Pending/Ready, verify dependencies succeeded/skipped, check freshness:

   - Skip up-to-date tasks (populate outputs).
   - Submit asynchronous execution of eligible tasks via thread pool.

5. **Deadlock & Completion Detection:**  
   Mark run complete if all tasks are terminal or if deadlock/cycle detected.

6. **Apply AI Completions:**  
   Integrate AI task completions when available, retry deferring if run is not active.

- Resolve inputs via `DataflowResolver`.
- Check freshness of input/output files to possibly skip task.
- Run tasks via `TaskExecutorRegistry`.
- Support task states including WaitingExternal for async external completions.
- Update run and task state consistently and safely.
- Generate workflow run IDs based on time and workflow ID.

---

## Thread Safety

- Internal data guarded by a mutex; public methods lock on access.
- Task execution and AI completions dispatched on separate threads.
- Designed to be tick-driven and non-blocking on the main thread.

# AIAssistant Event System Documentation

This module provides a type-safe, extensible event framework within the `AIAssistant` namespace, enabling representation, categorization, and dispatching of diverse system and application events.

---

## Enumerations

### `EventType`
Enumerates all supported event types:
- `None` — No event.
- `KeyPressed`, `KeyReleased` — Keyboard events.
- `MouseMoved`, `MouseButtonPressed`, `MouseButtonReleased` — Mouse events.
- `TimerElapsed` — Timer event.
- `FileAdded`, `FileRemoved`, `FileModified` — File system events.
- `AppError` — Application error.
- `EngineEvent` — Engine-specific event.
- `PythonCrashed` — Python environment crash event.

### `EventCategory`
Bitflags for event grouping:
- `NoneCategory = 0`
- `EventCategoryKeyboard = 1 << 0`
- `EventCategoryMouse = 1 << 1`
- `EventCategoryTimer = 1 << 2`
- `EventCategoryFileSys = 1 << 3`
- `EventCategoryApp = 1 << 4`
- `EventCategoryEngine = 1 << 5`

---

## Class: `Event`

Abstract base for all events.

### Members
- `bool m_Handled` — indicates if event is handled.

### Core Methods
- `virtual ~Event()` — base destructor.
- `bool IsHandled() const` — returns handled state.
- `void SetHandled(bool handled = true)` — sets handled state.
- `virtual EventType GetEventType() const = 0` — event type getter.
- `virtual const char* GetName() const = 0` — event name getter.
- `virtual int GetCategoryFlags() const = 0` — event categories flags.
- `bool IsInCategory(EventCategory category) const` — tests membership in category.
- `virtual std::string ToString() const` — string representation (default: event name).

---

## Class: `EventDispatcher`

Dispatches events to matching handlers in a type-safe manner.

### Constructor
- `EventDispatcher(Event& event)` — stores event reference.

### Template Method
- `template <typename T> bool Dispatch(std::function<bool(T&)> func)`
  - Checks if the stored event is of type `T`.
  - If yes, calls `func` with event cast to `T&`.
  - Sets event handled flag based on `func` return.
  - Returns `true` if dispatched, else `false`.

---

## Helper Macros

### `EVENT_CLASS_TYPE(type)`

Defines static and virtual methods for event type identification:
```cpp
static EventType GetStaticType() { return EventType::type; }
virtual EventType GetEventType() const override { return GetStaticType(); }
virtual const char* GetName() const override { return #type; }
```

### `EVENT_CLASS_CATEGORY(category)`

Defines virtual method returning category flags:
```cpp
virtual int GetCategoryFlags() const override { return category; }
```

---

## Usage Overview

1. Inherit from `Event` to define a new event type.
2. Use `EVENT_CLASS_TYPE` and `EVENT_CLASS_CATEGORY` in the event class.
3. Instantiate and pass events to `EventDispatcher`.
4. Call `Dispatch<T>` with handler functors tailored for event type `T`.
5. Use `IsInCategory` to query event categories.
6. Manage event propagation by checking/setting the handled state.

---

This system enables modular, clear, and efficient event-driven programming for keyboard, mouse, timer, filesystem, application, and engine events.

- Pushes event into internal queue.

Dequeue a single event.

- Locks mutex.
- Returns `nullptr` if empty.
- Otherwise returns and removes front event.

---

Dequeue all events.

- Locks mutex.

---

- Locks mutex.
- Returns queue size.

# TerminalManager Class Documentation

`TerminalManager` manages a terminal-based user interface for logging and status display using `pdcurses` (a curses library). It supports thread-safe logging, dynamic layout, color theming, and status callbacks, enabling efficient terminal UI updates in a multi-threaded environment.

---

## Namespace

```cpp
namespace AIAssistant
```

---

## Overview

- Initializes and manages curses terminal mode.
- Creates four windows: log header, log content, status header, and status content.
- Supports dynamic layout adapting to terminal resizing.
- Queues log lines safely from multiple threads and renders them incrementally.
- Allows client-supplied callbacks for:
  - Generating status lines.
  - Determining status pane height.

---

## Types

### StatusLinesCallback

```cpp
using StatusLinesCallback = std::function<void(std::vector<std::string>& lines, int maxWidth)>;
```

- User provides lines to display in the status window.
- `lines` receives zero or more strings.
- `maxWidth` is the available width for text.

### StatusHeightCallback

```cpp
using StatusHeightCallback = std::function<int(int totalRows)>;
```

- User determines the height of the status window.
- Input `totalRows` is total terminal rows.
- Returns the number of rows to allocate to status (minimum 1).

---

## Public Methods

### TerminalManager()

- Constructs the manager, no terminal UI initialized yet.

### ~TerminalManager()

- Cleans up and shuts down terminal mode if initialized.

### void Initialize()

- Enables curses mode and configures terminal (noecho, cbreak, keypad, cursor hiding).
- Applies color theme (green text if supported).
- Creates windows based on current terminal size.
- Idempotent; calling multiple times has no effect if initialized.

### void Shutdown()

- Releases all curses windows and ends curses terminal mode.
- Idempotent; no effect if not initialized.

### void Render()

- Handles terminal resize events and rebuilds layout if necessary.
- Drains and renders all queued log lines.
- Invokes status lines callback to render status window.
- Refreshes all windows.
- No effect if not initialized.

### void RenderPaused(int counter)

- Similar to `Render()`, but replaces log content with a pause message and a counter.
- Renders status as usual.
- No effect if not initialized.

### void EnqueueLogLine(std::string const& line)

- Thread-safe method to queue a log line for rendering.
- Lines are processed and displayed on the next `Render()` call.

### void SetStatusCallbacks(StatusLinesCallback statusLinesCallback, StatusHeightCallback statusHeightCallback)

- Sets user callbacks for generating the status content and determining status window height.
- Triggers immediate window layout recalculation.

---

## Internal Behavior

- Maintains four curses `WINDOW*`:
  - Log header (1 row)
  - Log content (variable rows)
  - Status header (1 row)
  - Status content (variable rows)
- Log content auto-scrolls when full.
- Locks pending log lines with a mutex for thread safety.
- Applies a custom green color if terminal supports color redefinition.
- Status window lines cleared and redrawn each render cycle.
- Headers drawn with bold text and horizontal lines.

---

## Usage Outline

1. Instantiate `TerminalManager`.
2. Call `Initialize()` before any rendering.
3. Optionally assign status callbacks via `SetStatusCallbacks`.
4. `EnqueueLogLine()` to add log entries safely from any thread.
5. Call `Render()` regularly to update UI.
6. Call `RenderPaused()` if displaying a paused state.
7. Call `Shutdown()` before exiting to restore terminal state.
