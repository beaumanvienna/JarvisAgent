# AIAssistant::Application Class Documentation

## Overview

`AIAssistant::Application` is an abstract base class that defines the interface for applications within the AI Assistant framework. It manages the application lifecycle, event handling, and startup status reporting.

## Class Definition

```cpp
namespace AIAssistant
{
    class Application
    {
    public:
        virtual ~Application() = default;

        virtual void OnStart() = 0;
        virtual void OnUpdate() = 0;
        virtual void OnEvent(std::shared_ptr<Event>&) = 0;
        virtual void OnShutdown() = 0;

        virtual bool IsFinished() const = 0;

        std::string const& GetFatalStartupMessage() const;

    protected:
        std::string m_FatalStartupMessage;
    };
}
```

## Member Functions

### Destructor

- `virtual ~Application() = default;`  
  Ensures proper cleanup of derived classes.

### Lifecycle Methods

- `virtual void OnStart() = 0;`  
  Called once when the application starts. Must be implemented by derived classes.

- `virtual void OnUpdate() = 0;`  
  Called repeatedly to update the application state. Must be implemented by derived classes.

- `virtual void OnShutdown() = 0;`  
  Called during application shutdown for cleanup. Must be implemented by derived classes.

### Event Handling

- `virtual void OnEvent(std::shared_ptr<Event>&) = 0;`  
  Handles events passed to the application. Must be implemented by derived classes.

### Status

- `virtual bool IsFinished() const = 0;`  
  Returns true if the application has completed and should exit. Must be implemented by derived classes.

### Startup Error Reporting

- `std::string const& GetFatalStartupMessage() const;`  
  Returns a message describing fatal errors that occurred during startup, if any.

## Protected Members

- `std::string m_FatalStartupMessage;`  
  Stores a descriptive message about any fatal startup error.

## Usage

Derive from `AIAssistant::Application` and implement all pure virtual methods to create a custom application. Use the lifecycle and event methods to control application behavior and respond to events. Use `m_FatalStartupMessage` to communicate critical startup errors.

# FileCategorizer Class Documentation

## Overview

The `FileCategorizer` class (namespace `AIAssistant`) is responsible for classifying, tracking, and managing files in an AI assistant application. It provides mechanisms to add, remove, and update file records, associating each file with a specific category (settings, tasks, context, requirements, etc.). The class also prevents processing of irrelevant, unsafe, or non-textual files, improving robustness and efficiency.

## Main Responsibilities

- **Categorize files** based on naming conventions, file content, magic numbers, and other heuristics.
- **Track all managed files** in categorized containers for efficient access and status checking.
- **Manage file status:** detect new, modified, deleted, ignored, or oversized files.
- **Synchronize file state** between actual files on disk and the application's tracked state.
- **Prevent unsafe or unhelpful files** (binaries, oversize, old PROB, outputs, etc.) from being processed by AI logic.

---

## Key Structures

### `TrackedFiles`

- Holds a map (`TrackedFileMap`) of file paths to `TrackedFile` objects.
- Provides methods to:
  - Access (`Get()`), write (`Write()`), and mark dirty state.
  - Count and manipulate "modified" tracked files.

### `CategorizedFiles`

Aggregates all `TrackedFiles` containers by category:
- `m_Settings`
- `m_Context`
- `m_Tasks`
- `m_Provider`
- `m_Requirements`
- `m_Subfolders`
- `m_Ignored`

---

## FileCategorizer Public API

### Constructor / Destructor

- `FileCategorizer()`: Default constructor.
- `~FileCategorizer()`: Destructor.

### File Operations

- `fs::path const AddFile(fs::path const& filePath)`
  - Categorizes and tracks a new file.
- `fs::path const RemoveFile(fs::path const& filePath)`
  - Removes a file from all tracked categories.
- `fs::path const ModifyFile(fs::path const& filePath)`
  - Marks an already tracked file as modified.

### Accessors

- `CategorizedFiles& GetCategorizedFiles()`
- `CategorizedFiles const& GetCategorizedFiles() const`
  - Access categorized file containers (read-write / const).
- `void PrintCategorizedFiles() const`
  - Prints the paths of all currently tracked files by category.

---

## File Categorization Logic

`FileCategorizer::Categorize(fs::path const&)` uses a combination of:

- **Directory checks**
- **Prefix matching:** File names starting with certain tokens (e.g. "STNG", "TASK") are mapped to categories.
- **Output and hidden file detection**
- **PROB file handling:** Identifies stale (before app startup) PROB files and ignores them; processes recent PROB files as requirements.
- **Magic number checks:** Detects common binaries (PDF, ZIP, DOCX, PNG, JPEG, ELF, PE, etc.) and ignores them.
- **Text-likeness check:** Skips files with >10% non-printable bytes.
- **File size check:** Ignores files exceeding configured size, creates companion ".output.txt" explanatory file.

If a file passes all checks and does not match a special category, it is tracked as a `Requirement`.

---

## Internal Helpers

- `FileCategory Categorize(fs::path const&) const`
  - Categorizes a file based on the above criteria.
- `void RemoveFromFiles(TrackedFiles&, fs::path const&)`
  - Removes a file from a specific category.

---

## Logging and Feedback

- Logs actions (addition, removal, ignore reasons, bad file types)
- Creates readable messages for rejected files (e.g., oversized)

---

## Summary Table

| Method | Purpose |
|--------|---------|
| `AddFile` | Add and categorize a file |
| `RemoveFile` | Remove from tracking |
| `ModifyFile` | Mark as modified |
| `PrintCategorizedFiles` | Print current tracking state |
| `GetCategorizedFiles` | Access categorized files |
| `Categorize` | Internal: decide category |

---

## Typical Use

1. Application adds files via `AddFile`.
2. As files change or are deleted, `ModifyFile` or `RemoveFile` are called.
3. Internal classification ensures only relevant, safe, and useful files are managed.
4. Application queries and processes files via `GetCategorizedFiles`.

---

## Notes

- Efficiently manages directory trees.
- Actively prevents accidental AI processing of unhelpful files.
- Ensures that files handled are fresh, relevant, and parsable by the AI system.
- Provides fine-grained file change tracking for synchronization and further actions.

# FileWatcher Class Documentation

## Overview

`AIAssistant::FileWatcher` is a C++ class that monitors a specified directory for file changes. It detects file additions, modifications, and removals in real-time (with a configurable interval), and issues corresponding events via the application's event system.

## Key Features

- Watches a directory (recursively) at a defined polling interval.
- Detects and notifies on file additions, modifications, and deletions.
- Ignores non-regular files and files beginning with a dot (hidden or temporary files).
- Runs watcher logic in a background thread using the application's thread pool.
- Sends events (`FileAddedEvent`, `FileModifiedEvent`, `FileRemovedEvent`) on file changes.
- Handles concurrent stop/start operations cleanly and safely.
- Shuts down watcher if the watched directory is deleted, pushing an `EngineEventShutdown` event.

## Public API

### Constructor

```cpp
explicit FileWatcher(const fs::path& pathToWatch, std::chrono::milliseconds interval = 100ms);
```

- `pathToWatch`: Path to the directory to be watched.
- `interval`: Polling interval in milliseconds (default: 100ms).

### Destructor

```cpp
~FileWatcher();
```

Stops the watcher if running.

### Methods

#### `void Start()`

Begins watching the specified directory. Does nothing if already running.

#### `void Stop()`

Stops the watcher and blocks until the internal thread has terminated.

#### `void SignalStop()`

Signals the watcher thread to stop (non-blocking).

#### `void WaitStop()`

Waits until the watcher thread has terminated.

## Internal Logic

### File Scanning

- At startup: Scans all existing files, filtering valid files, and fires an event for each.
- In each cycle:
  - Adds/updates: For new/modified files, emits the appropriate event.
  - Removals: For no-longer-existing files, emits removal events.
- If the watched directory is deleted, emits an engine shutdown event.

### Valid File Criteria

- Must be a regular file.
- Filename must not start with a dot (`.`).

## Thread Safety

- Uses atomic and mutex/condition_variable to guard the running state and stopping logic.
- Background watcher runs as a task in the core thread pool.

## Event Mechanism

- Uses `Core::g_Core->PushEvent` to send events for detected changes.
- Event types: `FileAddedEvent`, `FileModifiedEvent`, `FileRemovedEvent`, `EngineEventShutdown`.

## Use Cases

- Live-reloading resources in applications (edit-and-view loops).
- Notifying systems or users about file modifications/deletions/additions.
- Implementing sync or backup features where file changes need to be tracked.

## Example Usage

```cpp
AIAssistant::FileWatcher watcher("/path/to/dir", 200ms);
watcher.Start();

// ... application logic ...

watcher.Stop();
```

# AIAssistant::ProbUtils

## Overview

`AIAssistant::ProbUtils` is a C++ namespace providing utility functions for working with filenames used in a "PROB" file system. These files follow a strict naming convention that embeds an identifier and timestamp in the filename. The utilities allow you to parse, classify, and extract information from such filenames.

---

## Structures

### `ProbFileInfo`

Represents information extracted from a PROB filename.

| Member     | Type      | Description                                 |
|------------|-----------|---------------------------------------------|
| `id`       | uint64_t  | Numeric ID parsed from the filename         |
| `timestamp`| int64_t   | Timestamp parsed from the filename          |
| `isOutput` | bool      | True if the file is an output file, else false |

---

## Functions

### `std::optional<ProbFileInfo> ParseProbFilename(const std::string& filename)`

Parses a filename that matches PROB file naming conventions:
- Format for input: `PROB_<id>_<timestamp>.txt`
- Format for output: `PROB_<id>_<timestamp>.output.txt`

**Returns:**
- `ProbFileInfo` containing `id`, `timestamp`, `isOutput`
- `std::nullopt` if the filename does not match the PROB format, or parsing fails

### `bool IsProbFile(const std::string& filename)`

Checks if a filename matches the PROB file naming convention.

**Returns:**
- `true` if `ParseProbFilename` parses successfully
- `false` otherwise

---

## Usage Example

```cpp
#include "file/probUtils.h"

// Example usage
std::optional<AIAssistant::ProbUtils::ProbFileInfo> info =
    AIAssistant::ProbUtils::ParseProbFilename("PROB_12345_1717890172.output.txt");

if (info) {
    // Access info->id, info->timestamp, info->isOutput
}
```

---

## Notes

- Only files prefixed with `PROB_` and suffixed with `.txt` or `.output.txt` are recognized.
- Improperly formatted filenames return `std::nullopt`.
- Exception safety: Parsing errors are caught, returning `std::nullopt` rather than throwing.

# ScriptRegistry Class Documentation

**Namespace:** `AIAssistant`

## Overview

`ScriptRegistry` manages the discovery, parsing, registration, and lookup of script files (Python `.py`, Bash `.sh`, PowerShell `.ps1`) in a specified directory. It extracts structured metadata from script headers for use by humans and AI agents, supporting features like markdown summary tables and lookups by path/module.

## ScriptRegistryEntry

Represents metadata for a single registered script.

- `m_FilePath`: Script file path.
- `m_Short`: Short description (from script header).
- `m_Description`: Longer description (from script header).
- `m_Params`: List of parameter descriptions.
- `m_Outputs`: List of output descriptions.
- `m_ExportedFunctions`: List of exported function names.

## ScriptRegistry Public Interface

### void ScanDirectory(const std::filesystem::path& scriptsDir)
Scans recursively for `.sh`, `.py`, and `.ps1` scripts in `scriptsDir`, parses script headers, and populates the registry with valid entries.

### void AddOrUpdate(const std::filesystem::path& filePath)
Parses and adds/updates the registry entry for a single script file. If the script no longer qualifies (e.g., marker removed), it is unregistered.

### void Remove(const std::filesystem::path& filePath)
Removes the specified script from the registry.

### std::string SerializeMarkdownTable() const
Returns a markdown table listing all registered scripts, their short descriptions, and parameters—useful for human or AI-readable documentation.

### std::vector<ScriptRegistryEntry> GetEntries() const
Returns a snapshot (`std::vector`) of all current registry entries.

### size_t Size() const
Returns number of scripts currently registered.

### ScriptRegistryEntry const* FindByModulePath(const std::string& modulePath) const
Finds an entry by Python module path (e.g., `"scripts.parseLog"` → `"scripts/parseLog.py"`).

### ScriptRegistryEntry const* FindByFilePath(const std::string& filePath) const
Finds an entry by (relative) file path. Supports both exact and suffix matching.

## Script Header Format

Scripts must contain an `@jarvis-script` marker within their first 20 lines, followed by header comment lines with the following fields:

- `@short:` Short, one-line description (required)
- `@params:` (optional, repeatable) Parameter description(s)
- `@description:` (optional) Longer description
- `@outputs:` (optional, repeatable) Output description(s)

Fields are parsed from comment lines (`# ...`).

## Thread Safety

All public methods are thread-safe via internal mutex (`std::mutex m_Mutex`).

## Usage Example

```cpp
ScriptRegistry registry;
registry.ScanDirectory("scripts");
std::string markdown = registry.SerializeMarkdownTable();
auto entries = registry.GetEntries();
```

## Purpose

ScriptRegistry enables fast, structured, and reliable introspection of scripts for automation, documentation, and AI-assistant features, including context injection and lookup for code execution.

# TrackedFile Class Documentation

## Overview

`TrackedFile` is a C++ class in the `AIAssistant` namespace designed to represent and manage a file on disk that is tracked for changes. It maintains information about the file's path, category, and modification status, and provides thread-safe access to its content.

## Purpose

Tracks and manages a single file, allowing users to:

- Monitor file modification state.
- Retrieve file content safely.
- Categorize files logically.

## Usage

### Public Interface

#### Constructor

```cpp
TrackedFile(fs::path const& path, FileCategory fileCategory);
```
Initializes a tracked file at the given path and assigns a category.

#### Methods

- `bool IsModified() const`
  - Returns whether the file is marked as modified.

- `fs::path const& GetPath() const`
  - Returns the path of the tracked file.

- `void MarkModified(bool modified = true)`
  - Sets the modification status. Default marks as modified.

- `std::string GetContent()`
  - Reads and returns the file content. Thread-safe. Logs a warning if the file cannot be opened.

- `FileCategory GetCategory() const`
  - Returns the category of the file.

### Thread Safety

- Access to file content via `GetContent()` is synchronized with a mutex.
- Modification flag is atomic for safe concurrent updates.

## Data Members

- `m_Path` (`fs::path`): Path to the file.
- `m_FileCategory` (`FileCategory`): Logical file category.
- `m_Modified` (`std::atomic<bool>`): Indicates if the file has been modified.
- `m_Mutex` (`std::mutex`): Protects file content retrieval.

## Example

```cpp
TrackedFile trackedFile("example.txt", FileCategory::Source);
if (trackedFile.IsModified()) {
    std::string content = trackedFile.GetContent();
```

# PythonEngine Class Documentation

The `PythonEngine` class is a C++ wrapper for embedding and managing a Python interpreter within a multi-threaded C++ application. It is designed to run Python scripts in a controlled manner, provide C++/Python hooks for start, update, event, and shutdown, and facilitate workflow task execution with controlled input/output.

## Overview

`PythonEngine` handles:

- Loading and initializing a Python script as a module.
- Redirecting Python's stdout/stderr to the C++ logging system.
- Supporting hot-reloading Python modules on workflow invocations.
- Dispatching lifecycle hooks (`OnStart`, `OnUpdate`, `OnEvent`, `OnShutdown`) to Python, if defined.
- Managing workflow tasks as queued jobs, passing them to Python functions, and returning structured results.
- Ensuring thread safety and avoiding Global Interpreter Lock (GIL) deadlocks.
- Graceful shutdown and resource cleanup.

## Public API Summary

| Method                                                                          | Description                                                                                                                                                                     |
|----------------------------------------------------------------------------------|---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `PythonEngine()` / `~PythonEngine()`                                             | Constructor/destructor. Initializes or cleans up the engine state.                                                                                                               |
| `bool Initialize(const std::string& scriptPath)`                                 | Loads the main Python script/module at `scriptPath`, sets up hooks and redirection, and spawns the worker thread. Returns `true` on success.                                    |
| `void Stop()` <br> `void SignalStop()` <br> `void WaitStop()`                    | Shuts down the Python interpreter in a graceful and thread-safe way. <br> `SignalStop` notifies the worker thread to stop. <br> `WaitStop` blocks until cleanup is complete.    |
| `void OnStart()`                                                                 | Enqueues and invokes the `OnStart()` hook in Python, if defined.                                                                                                                 |
| `void OnUpdate()`                                                                | Enqueues and invokes the `OnUpdate()` hook in Python, if defined.                                                                                                                |
| `void OnEvent(std::shared_ptr<Event> eventPtr)`                                  | Enqueues and invokes the `OnEvent(event)` hook in Python, if defined, passing C++ `Event` data to Python.                                                                        |
| `bool IsRunning() const`                                                         | Returns `true` if the Python engine and worker thread are running.                                                                                                               |
| `bool ExecuteWorkflowTask(TaskDef const&, std::string const&, ...)`              | Executes a workflow task as a Python function. Inputs/outputs are via string key-value maps with context, working dir, and params JSON. Block until the Python call completes.   |

## Key Private/Internal Methods

- `void Reset()`: Resets state and releases Python references.
- `void EnqueueTask(const PythonTask&)`: Adds a new task to the queue for the worker thread.
- `void StartWorkerThread()` / `void WorkerLoop()`: Thread handling for processing queued events/tasks under GIL.
- `void CallHook(PyObject*, const char*)`: Calls a specific Python function without event arguments.
- `void CallHookWithEvent(PyObject*, const char*, const Event&)`: Calls a hook passing a C++ event as a Python dict.
- `void ExecuteWorkflowTaskOnWorker(std::shared_ptr<WorkflowTaskRequest> const&)`: Handles the real Python workflow call on the worker thread, manages Python exception capturing, and result extraction.

## Workflow Task Execution

- Each workflow task specifies its target Python module/function via JSON (`{"module": "modulename", "function": "funcname"}`).
- Input and context key-value maps are passed as Python kwargs and a context dict.
- Captures Python stdout/stderr output, as well as any exceptions, returning them to the C++ caller.
- Handles hot-reloading of the target Python module per task, so code changes are picked up immediately.
- Result from Python must be a dict (or `None`). Result keys/values copied to C++ output map as strings.

## Lifecycle, Threading, and Safety

- A dedicated worker thread manages all Python execution and holds the GIL as needed.
- Task queue ensures serial execution and correct synchronization of Python calls.
- C++/Python hooks can be attached/omitted in Python (`OnStart`, `OnUpdate`, `OnEvent`, `OnShutdown`).
- Handles GIL release/acquire and mutex locking/unlocking to avoid deadlocks.
- Cleans up references and restores interpreter state on shutdown.

## Python Redirection & Logging

- Redirects Python script's stdout and stderr to C++ logging using a custom Python class that calls back to C++.
- All errors and exceptions are logged for visibility and debugging.

## Example Usage

```cpp
AIAssistant::PythonEngine engine;

if (engine.Initialize("my_script.py")) {
    engine.OnStart();

    // Later, respond to an event
    auto myEvent = std::make_shared<MyCustomEvent>();
    engine.OnEvent(myEvent);

    // Execute workflow task
    TaskDef taskDef = ...;
    std::unordered_map<std::string, std::string> input, context, output;
    std::string error, stdout, stderr;
    bool ok = engine.ExecuteWorkflowTask(taskDef, "/tmp", input, context, output, error, stdout, stderr);

    // Shutdown
    engine.Stop();
}
```

- All Python function names and parameters are case sensitive.
- For correct hot-reloading, target Python modules/functions must exist and be callable as specified in the task defs.

## Overview

`ChatMessagePool` is a C++ class designed to manage chat messages in an AI Assistant context.   - `bool answered` — True if the message has been answered.

#### Constructor

- **`uint64_t AddMessage(const std::string& subsystem, const std::string& message);`**

  - Returns the unique message ID.

- **`void MarkAnswered(uint64_t id, const std::string& answerText);`**

- **`void Update();`**
  - Calls `RemoveExpired()`. Intended for periodic invocation.

- **`size_t Size() const;`**
  - Returns the total size of the pool.

- **`size_t ActiveCount() const;`**
  - Returns the number of currently active (unanswered and non-expired) entries.

---

- Grows the pool automatically if usage exceeds `growThreshold`.
- Uses a queue to manage free indices for efficient allocation.
- Thread-safe via `std::mutex` locking.

---

## Usage Pattern

1. Create a `ChatMessagePool` instance.
2. Use `AddMessage()` to insert messages from users or subsystems.
3. Periodically call `Update()` (e.g., via timer) to remove expired messages.
4. Use `MarkAnswered()` when an AI or human provides an answer, to mark and notify.
5. Monitor `Size()` and `ActiveCount()` for status/metrics.

## Thread Safety

All methods that modify state are protected with a mutex for safe concurrent access.

# AiRequestPool Class Documentation

## Overview

`AiRequestPool` is a thread-safe C++ class designed to manage and track lifecycle events of asynchronous AI call requests in a workflow or pipeline—typically where the completion is signaled via output files on disk. It enables registering, monitoring, and consuming results for multiple in-flight AI requests, with robust handling of timeouts, file-based signaling, and deterministic output mapping.

Key features:

- Registers AI requests and tracks them until completion or failure.
- Supports both legacy (file-naming-pattern-based) and new (path-based) completion mechanisms.
- Handles all synchronization and is safe for use across multiple threads.
- Maintains deadline (timeout) and file-activity watchdogs for each registered request.
- Provides non-blocking and blocking options for consuming results.
- Supports deterministic output mapping for workflow task execution.

---

## Key Data Types

### `AiRequestHandle`
Encapsulates a unique identifier (`requestId` and `requestTimestampNs`) for each AI request.  
- **Method:** `IsValid()` – Checks if the handle is valid.

### `AiRequestCompletion`
Holds the result of a completed AI request workflow task:
- Workflow, run, and task identifiers.
- Success/failure info, response text, and error message.
- Map of named outputs (always file paths).

---

## Usage

### Registration

- **AllocateRequestId()**  
  Allocates and returns a unique int64_t requestId.  
  _Use this when constructing a new AiRequestHandle._

- **RegisterPending()**  
  Registers a request for tracking, with an optional timeout.  
  Returns the handle to use for further polling/consumption.

- **RegisterPendingWorkflowTask()**  
  Preferred path for workflow-based tasks. Associates request with task info and expected outputs (paths and slot names). Registers file paths for path-based event matching.

### Matching Output Events

- **OnProbFileEvent()**  
  Legacy: Consume an event based on PROB_<id>_<ts> file naming, marking the request as completed or failed.

- **OnOutputFileCreated()**  
  Path-based: Trigger completion of the request if a registered expected output file is created.

- **OnCurlDispatched()**  
  Informs the pool that a corresponding outbound curl is dispatched, activating the main timeout.

- **KickFileActivityWatchdog()**  
  Notifies the pool that file activity occurred (e.g., a file write), resetting the file-activity deadline.

### Consuming Results

- **TryConsumeResult()**  
  Non-blocking: Returns result and removes it from the pool, if completed. Otherwise returns false.

- **TryPopCompletion()**  
  Non-blocking: Pops the next queued `AiRequestCompletion`. For workflow runtimes using tick-based polling.

- **WaitForCompletion()**  
  Blocking: Waits until the request is completed or timeout.

- **Forget()**  
  Removes a request from the pool, regardless of completion.

### Maintenance

- **Update()**  
  Call periodically. Applies timeouts and triggers any watchdogs for requests lacking activity or slow completions.

- **Shutdown()**  
  Marks the pool as shutting down and fails all pending requests.

---

## Notes on Behavior

- **Thread Safety:** Internally uses mutexes to guard all shared state.
- **Completion/Deduplication:** Skips duplicate events or completion for already-consumed requests.
- **File-based Triggers:** All completions are ultimately signaled via file creation for robust inter-process communication.
- **Error Handling:** If any step (output file write, read, etc.) fails, the request is failed and an error message is recorded.
- **Output Value Mapping:** Determines which output file path maps to which slot, consistently and deterministically, supporting explicit and implicit outputs.

---

## Typical Usage Pattern

1. Allocate a requestId and timestamp; construct an `AiRequestHandle`.
2. Use `RegisterPending` or `RegisterPendingWorkflowTask` to register the request with the pool.
3. On file creation or AI backend response, call either `OnProbFileEvent` or `OnOutputFileCreated` as appropriate.
4. Periodically call `Update()` to handle timeouts.
5. Use `TryConsumeResult` or `TryPopCompletion` as needed to drain results or act on completions.
6. On shutdown or cleanup, call `Shutdown()`.

---

## Example

```cpp
AIAssistant::AiRequestHandle handle;
handle.requestId = pool->AllocateRequestId();
handle.requestTimestampNs = /*...*/; // e.g., current monotonic ns

pool->RegisterPendingWorkflowTask(
    handle, "workflowId", "runId", "taskId",
    outputPaths, outputSlotNames, timeoutMs, expectedOutputPath);

// ... in file watcher event loop:
pool->OnOutputFileCreated(filePath); // or OnProbFileEvent(...);

// ... in main event loop:
pool->Update();

// ... poll for result non-blocking:
bool wasFailed;
std::string response, error;
if (pool->TryConsumeResult(handle, wasFailed, response, error)) {
    // handle result
}
```

---

| Method                           | Description                                                   |
|-----------------------------------|---------------------------------------------------------------|
| AllocateRequestId                 | Generates a new unique request ID                             |
| RegisterPending                   | Registers a generic pending AI request                        |

## Public Methods

### `optional<TaskResolvedInputs> ResolveInputsForTask(const WorkflowDefinition&, const WorkflowRun&, const TaskDef&, const std::string& taskId) const`
Resolves all declared inputs for a given task instance.

#### Resolution Order:
1. Explicit dataflow edge (output from another task)
2. Workflow run context variable
3. Default value (`m_Default` from input definition)

- If a required input is not resolved by any of these, returns a `TaskResolvedInputs` with an error message.
- Before returning, expands any templates (e.g., `{{inputs.x}}`) in the resolved input values.

- `TaskResolvedInputs` with resolved values (if successful)

Expands template variables in a string (e.g., replaces `{{inputs.x}}` with the resolved value for `x`).

#### Returns:
- `true` if all templates are resolved successfully.

1. To run a task in a workflow, call `ResolveInputsForTask` to gather all required input values for a given task instance.
2. If every required input is resolved (by dataflow, context, or default), the result will be ready-to-use, including any necessary template expansions.

## Overview

`QueryParser` parses and evaluates Lucene-style queries against documents represented as key-value maps (field → value). It provides fast parsing, an easy-to-use API, and efficient evaluation for query filtering use cases.

---

## Query Syntax

- **AND / OR / NOT** operators — support for precedence and grouping.
- **Field match:** `field:value` (supports wildcards: `*` for prefixes)
- **Negation:** `-field:value` (same as `NOT field:value`)
- **Range:** `field:[lo TO hi]`, `field:{lo TO hi}`, inclusive or exclusive
- **Grouping:** Use parentheses: `( ... )`

---

## Main Components

### Query AST (`QueryNode`)

Defines node types for the Abstract Syntax Tree:
- **And, Or, Not**: Logical operations
- **FieldMatch**: Direct (or wildcard) value match for a field
- **FieldRange**: Range matching for a field

Each node has relevant fields and children depending on type.

### QueryDocument

Aliased as `std::unordered_map<std::string, std::string>`. Represents a document with field values.

---

## QueryParser Public API

### Methods

#### 1. `std::unique_ptr<QueryNode> Parse(const std::string& queryString, std::string& errorMessage) const;`
- Parses a Lucene-style query string to an AST (`QueryNode` tree).
- On failure, returns `nullptr` and sets `errorMessage`.

#### 2. `static bool Matches(const QueryNode& node, const QueryDocument& doc);`
- Evaluates if the given document matches the parsed query AST.

---

### Tokenizer

Includes a simple tokenizer:
- Recognizes parentheses, brackets, colons, operators, quoted strings, fields, values, wildcards, and ranges.
- Tokens are accessible via the `Token` struct.

---

## Parsing & Evaluation Flow

1. **Tokenization:** Input is tokenized into discrete tokens (words, quotes, parens, etc.).
2. **Recursive Descent Parse:** Implements grammar for AND, OR, NOT, grouping, and field/range/value expressions.
3. **AST Construction:** Produces a `QueryNode` tree representing logical structure of the query.
4. **Evaluation:** Checks a `QueryDocument` against the AST efficiently.
   - AND: all children must match
   - OR: any child matches
   - NOT: negates child result
   - FieldMatch: checks field for exact or prefix (wildcard) match
   - FieldRange: field must fall within range (numeric if possible, else lexicographic)

---

## Grammar Supported

| Syntax                   | Description          | Example                             |
|--------------------------|---------------------|-------------------------------------|
| Logical ops AND, OR, NOT | Boolean logic       | `a:foo AND (b:bar OR NOT c:baz)`    |
| Field matches            | Field equality      | `title:hello`                       |
| Wildcard match           | Prefix match        | `user:adm*`                         |
| Field range              | Range inclusion     | `age:[18 TO 65]`                    |
| Grouping                 | Parentheses         | `(foo:bar OR user:adm*) AND active:yes` |
| Negation                 | Prefix minus        | `-disabled:true`                    |

---

## Example Usage

```cpp
AIAssistant::QueryParser parser;
std::string errorMsg;
auto ast = parser.Parse("status:active AND age:[18 TO 30]", errorMsg);
if (!ast) {
    // handle error: errorMsg
}

// Document to test

// matches == true
```

## Notes

- Field values are treated as strings. Range comparisons attempt numeric comparison first; if not possible, fall back to string comparison.
- Wildcard matches only support suffix `*` (prefix matching).
- Queries with syntax errors will populate `errorMessage`.

## Overview

`TaskFreshnessChecker` evaluates whether a workflow task is "up to date" by comparing input and output file timestamps, using logic similar to a Makefile:

- **All declared outputs** of the task must exist.
- **Oldest output file timestamp** must be **greater than or equal to** the **newest input file timestamp**.
- **Inputs** include both the task's explicit inputs and all outputs of upstream tasks it depends on.

If any output is missing or older than any input/upstream output, the task is considered not up to date.

---

## Key Concepts

- **WorkflowDefinition**: Contains the workflow structure and all tasks.
- **TaskDef**: Structure describing an individual task (not shown in full here).
- **Inputs**: Files declared as task inputs.
- **Outputs**: Files declared as task outputs.
- **Upstream outputs**: Outputs from direct and indirect dependency tasks.

---

## Main Member Functions

### `bool IsTaskUpToDate(...) const`
Checks if a specified task is up to date.

**Parameters:**
- `workflowDefinition`: The workflow structure with all task definitions.
- `taskId`: The task to check.
- `resolvedPaths`: Struct containing resolved input and output paths for the task.
- `resolveOutputPaths`: Callback for retrieving outputs of a task.
- `comparedInputPath` (optional): Receives the "latest" input path used in the check.
- `comparedOutputPath` (optional): Receives the "earliest" output path used in the check.

**Returns:**  
`true` if all outputs exist and are at least as new as all inputs/upstream outputs; `false` otherwise.

---

### `bool CollectUpstreamOutputTimes(...) const`
Recursively gathers modification times for outputs of all dependency tasks (direct and indirect).

**Parameters:**
- `workflowDefinition`: The workflow structure.
- `taskId`: The dependency task to examine.
- `visitedTasks`: Tracks previously visited tasks to avoid cyclic recursion.
- `outTimes`: Receives (path, timestamp) pairs for outputs.
- `resolveOutputPaths`: Callback to resolve output paths for a given task.

**Returns:**  
`true` if output times collected successfully for all dependencies; `false` if any output is missing or can't be read.

---

## Usage Summary

`TaskFreshnessChecker` is generally called by a workflow or pipeline system to decide if individual tasks need to be re-run (i.e., if their outputs are stale relative to their inputs or upstream dependencies).

---

## Implementation Notes

- Follows classical Makefile logic, extended to handle transitive task dependencies.
- Defensive: Returning `false` (not up to date) if any required file is missing or cannot be stat-ed.
- Designed for deterministic, explicit build or workflow orchestration.

# AIAssistant Template Engine

## Overview

The `AIAssistant::ExpandTemplate` function provides a unified template expansion engine for strings containing `{{...}}` placeholders. It is designed to expand placeholders in configuration files, commands, or scripts, supporting a predefined set of patterns. This allows both humans and AI systems to easily customize or generate text with dynamic values, such as file names, environment variables, or contextual inputs and outputs.

## Supported Placeholder Patterns

- `{{inputs}}`  
  Expands to a space-separated list of all input files.

- `{{outputs}}`  
  Expands to a space-separated list of all output files.

- `{{input[N]}}`  
  Expands to the N-th input file (0-based index).

- `{{output[N]}}`  
  Expands to the N-th output file (0-based index).

- `{{slot.NAME}}`  
  Looks up `NAME` in `inputValues` (named slots/inputs).

- `{{env.NAME}}`  
  Looks up `NAME` in environment variables.

- `{{inputs.NAME}}`  
  Cross-reference: looks up `NAME` in `inputValues`.

- `{{anything_else}}`  
  Bare name lookup in `inputValues`.

## Modes

- **Strict mode**  
  Unknown keys or out-of-bounds indices produce an error (used for shell tasks or critically-validated templates).

- **Lenient mode**  
  Unknown keys expand to an empty string (used for AI calls, per-item substitution, or when partial data is acceptable).

## Data Context Structure

`TemplateContext` supplies data to the engine:

```cpp
struct TemplateContext {
    std::vector<std::string> const* m_FileInputs;
    std::vector<std::string> const* m_FileOutputs;
    std::unordered_map<std::string, std::string> const* m_InputValues;
    std::unordered_map<std::string, std::string> const* m_EnvVariables;
};
```

- **m_FileInputs**: List of input filenames (optional).
- **m_FileOutputs**: List of output filenames (optional).
- **m_InputValues**: Map of input values by name (optional).
- **m_EnvVariables**: Map of environment variables (optional).

## API Reference

### Enum: `TemplateMode`

- `Strict`: Errors on unknown keys or malformed templates.
- `Lenient`: Ignores errors; unknowns produce empty replacement.

### Function: `ExpandTemplate`

```cpp
bool ExpandTemplate(
    std::string const& templateText,
    TemplateContext const& context,
    TemplateMode mode,
    std::string& expandedOut,
    std::string& errorMessage)
```

#### Parameters

- `templateText`: The string with placeholders to expand.
- `context`: Supplies input/output names, variables, and values.
- `mode`: Determines error handling (`Strict` or `Lenient`).
- `expandedOut`: Output parameter. Receives the expanded string.
- `errorMessage`: Output parameter. Description if expansion fails (strict mode).

#### Returns

- `true` if the template was expanded successfully.
- `false` if expansion failed (strict mode); errorMessage is set with a description.

## Usage Example

```cpp
AIAssistant::TemplateContext ctx = {
    &inputs,     // std::vector<std::string>
    &outputs,    // std::vector<std::string>
    &values,     // std::unordered_map<std::string, std::string>
    &env         // std::unordered_map<std::string, std::string>
};

std::string result, error;
bool ok = AIAssistant::ExpandTemplate(
    "cp {{input[0]}} {{output[0]}}; echo {{env.USER}}", ctx,
    AIAssistant::TemplateMode::Strict, result, error);

if (ok) {
    // use result
} else {
    // handle error
}
```

## Error Handling

- In strict mode, malformed templates (e.g., missing `}}`), unknown keys, or bad indices stop processing and provide a clear error message.
- In lenient mode, missing keys are replaced by empty strings and expansion continues.

# WorkflowRuntimeManager

The `WorkflowRuntimeManager` is a core class managing the runtime execution, state tracking, and lifecycle of workflow runs in a tick-based, non-blocking way. This class provides a robust, thread-safe interface for running, cancelling, pausing, and cleaning up workflow runs, supporting advanced features such as per-item parallelization, external AI calls, outputs management, branching control flow, retry/backoff, and integration with REST APIs/UI.

## Key Features

- **Workflow Run Management:** Start, stop, pause, resume, and monitor workflow runs.
- **Concurrency:** Runs workflow tasks asynchronously, using a thread pool and non-blocking tick/update pattern.
- **Task Lifecycles:** Handles complex per-task state transitions, execution (including re-tries), and handles outputs/errors.
- **Control Flow:** Implements DAG-based workflows with support for conditional branches and error handling.
- **Per-item Fan-out:** Efficiently manages per-item (array/map) parallelization using filtering and manifest diff for freshness/skipping.
- **External AI Calls:** Integrates with asynchronous, out-of-process AI request pools, propagating completions and context.
- **Resource Cleanup:** Cleans up workflow-generated files and directories, ensuring only workflow artifacts are affected.
- **Watchdog Support:** Monitors task inactivity and supports external heartbeats for long-running tasks/processes.
- **Thread-safe Snapshots:** Provides consistent snapshots of workflow and task state for use in APIs and UIs.

This approach ensures AI calls are contextually relevant, enforce system rules, and enable advanced features (such as multi-turn tool calls and persistent memory).

## Key Use Case

The class is used when generating input for an assistant AI call in the JarvisAgent system. It bundles all relevant context and rules for the AI agent to process and respond to user queries, optionally enabling tool integration and advanced workflow interactions.

### `struct AssembledPrompt`

- `stng`: System prompt (maps to `STNG_settings.txt`)
- `task`: Task instructions (maps to `TASK_instructions.txt`), usually fixed.
- `cntx`: Conversation context/history (maps to `CNTX_context.txt`)
- `prob`: Current user message (maps to `PROB` file, triggers the AI call)

  - `userMessage`: The latest message from the user.
  - `toolDescriptions`: (Optional) Descriptions and rules for tool APIs accessible to the AI.
- **Returns**: `AssembledPrompt`—a ready-to-use, multi-section prompt for an AI model.

  - Appends special tool-call instructions and descriptions if `toolDescriptions` is provided.

## How it Works

1. **Assemble()** is called with recent conversation and the user’s current query.

# WorkspaceIndexer Documentation

## Overview

`WorkspaceIndexer` is a thread-safe C++ class that scans, indexes, and manages metadata for source files within a workspace. It is designed for efficient lookup, relevance-based searching, and persistent caching of file summaries (such as AI-generated descriptions) to accelerate intelligent code assistance workflows.

---

## Key Features

- **Automatic File Indexing**: Scans configured directories for code and relevant text files, building an index of their paths, extensions, sizes, and modification times.
- **Summary Caching**: Stores and retrieves AI-generated per-file summaries, invalidating and evicting them automatically if the underlying file changes.
- **Fast Lookup and Full-Text Search**: Enables searching indexed files using query keywords, with results sorted by relevance based on path and summary content.
- **Persistent Storage**: Serializes the file index to a JSONL file for quick reloads, avoiding redundant rescans; supports partial incremental updates.
- **Thread Safety**: All public methods acquiring and holding an internal mutex, making the class safe to use from multiple threads.
- **Security & Filtering**: Restricts file access to the workspace and avoids scanning or indexing sensitive or irrelevant directories.

---

## Usage

### Construction

```cpp
AIAssistant::WorkspaceIndexer indexer("/path/to/index/dir");
```

Specify the directory to hold persistent index data (e.g., `assistant/index/`).

---

### Indexing and Scanning

#### `void ScanWorkspace()`

Performs a full scan of the workspace, starting from configured directories, and updating the index. Only new, modified, or removed files are reflected. Cached summaries are preserved when possible.

---

### Summary Access

#### `std::string GetFileSummary(const std::string& relativePath) const`

Returns the cached summary of the given file, or an empty string if none exists or it is stale (file modified since summary was generated).

#### `void SetFileSummary(const std::string& relativePath, const std::string& summary)`

Stores an AI-generated summary for a file, updating the cache and marking it with the file's current modification time.

#### `static std::string ReadFileContent(const std::string& relativePath, size_t maxBytes = 32768)`

Reads and returns up to `maxBytes` bytes of file contents for summarization or analysis. Returns an empty string for paths outside the workspace, errors, or unreadable files.

---

### Relevance Searching

#### `std::vector<FileIndexEntry> GetRelevantFiles(const std::string& query, int maxResults = 5) const`

Performs a keyword-based search across all files with cached summaries. Returns the most relevant matching entries up to `maxResults`, scored on both path and summary content.

---

### Statistics and Listing

#### `size_t FileCount() const`

Returns the total number of files currently indexed.

#### `size_t SummaryCount() const`

Returns the number of files for which a valid (non-stale) summary is cached.

#### `std::chrono::steady_clock::time_point LastScanTime() const`

Returns the timestamp of the last workspace scan.

#### `std::vector<FileIndexEntry> GetAllEntries() const`

Returns all file entries currently known to the indexer.

---

## FileIndexEntry Structure

Each indexed file is represented by:

| Field           | Description                                  |
|-----------------|----------------------------------------------|
| `relativePath`  | Path relative to workspace root              |
| `extension`     | File extension (e.g., ".cpp", ".md")         |
| `sizeBytes`     | File size in bytes                           |
| `mtimeNs`       | Modification time (nanoseconds since epoch)  |
| `summary`       | Cached AI-generated summary (if any)         |
| `summaryMtimeNs`| File mtime when summary was generated        |

---

## Implementation Notes

- **Supported File Types:** Scan is limited to code, markup, and related text files based on extension whitelist.
- **Directory Filtering:** Common build/vendor/temp folders are skipped to reduce noise and speed up scanning.
- **Persistence:** Index is written as `file_index.jsonl` in the specified directory. Summaries are stored inline with metadata.
- **Full-Text Querying:** Uses basic tokenization and substring search for matching.

---

## Thread Safety

All public methods lock an internal mutex. Safe for concurrent read/write access from multiple threads.

---

## Typical Workflow

1. **Initialize** the indexer, specifying the index directory.
2. **Call `ScanWorkspace`** to (re-)build the file index and load previous summaries.
3. **For each file,** call `GetFileSummary`; if empty, perform summarization via AI, then call `SetFileSummary`.
4. **Search** for relevant files using `GetRelevantFiles` with user or AI-generated queries.
5. **Regularly** call `ScanWorkspace` to pick up file changes and maintain summary validity.

---

## Example

```cpp

for (const auto& entry : indexer.GetAllEntries()) {
    std::string summary = indexer.GetFileSummary(entry.relativePath);
    if (summary.empty()) {
        // Generate summary using AI, then cache:
        std::string content = AIAssistant::WorkspaceIndexer::ReadFileContent(entry.relativePath);
        std::string newSummary = GenerateSummary(content);
        indexer.SetFileSummary(entry.relativePath, newSummary);
    }
}

// Search for relevant files about a keyword:
auto matches = indexer.GetRelevantFiles("database query", 5);
```

# Documentation: `engine` Function and C++ Integration in JarvisAgent

## Overview

The C++ code provided implements the main entrypoint function `engine(int argc, char* argv[])` for the JarvisAgent backend. This backend is responsible for initializing application state, validating configuration, managing keys, dispatching core services and application logic, and conducting orderly startup and shutdown. ## Function Purpose

The `engine` function initializes, configures, and runs the JarvisAgent backend engine. It:

- Parses command-line arguments, handling `--help` and `--version` gracefully.
- Validates presence of `config.json` and parses the engine configuration.
- Initializes logging, key management, and application state.
- Manages key loading with fallback to environment variables.
- Starts the core engine, launches the JarvisAgent application, and enters the main event loop.
- Handles application and core shutdown, with a watchdog for termination assurance.

---

## Command-Line Handling

- Recognizes `--help`/`-h` and `--version`/`-v`, printing usage or version and exiting.
- Rejects unknown command-line options with an error message and does not proceed.

---

## Configuration & Initialization Steps

1. **Configuration File:**  
   Looks for `config.json` in the current working directory; fails if missing.

2. **Logging:**  
   Initializes logger, providing macros for logging at multiple levels (trace, info, warn, error, critical). If not a distribution build, logging and asserts are enabled.

3. **Configuration Parsing:**  
   Uses `ConfigParser` to parse engine configuration from `config.json`. Checks if configuration was parsed successfully and validates it with `ConfigChecker`.

4. **Key Management:**  
   - Tries to load encrypted keys from `keys.json.enc` using the `JARVIS_MASTER_PASSWORD` environment variable.
   - If unable, tries to load unencrypted `keys.json`.
   - As a last resort, falls back to `OPENAI_API_KEY` or equivalent env vars.
   - Logs warnings if no usable keys are found.

5. **Engine Startup:**  
   - Constructs the main `Core` engine object.
   - Initializes and starts the JarvisAgent application via `app->OnStart()` and `engine->Run(app)`.

---

## Runtime Features

# AIAssistant Event System Documentation

This document provides an overview of the event system implemented in the provided C++ code. The event system facilitates handling various events (keyboard, mouse, file, timer, app, etc.) within an application. It consists of base classes, event type/category enumerations, and a flexible event dispatcher.

---

## EventType Enum

Defines possible types of events:

- `None`: No event.
- `KeyPressed`, `KeyReleased`: Keyboard events.
- `MouseMoved`, `MouseButtonPressed`, `MouseButtonReleased`: Mouse events.
- `TimerElapsed`: Timer event.
- `FileAdded`, `FileRemoved`, `FileModified`: File system events.
- `AppError`: Application error.
- `EngineEvent`: Engine-related event.
- `PythonCrashed`: Python interpreter crash event.

## EventCategory Enum

Bitflags representing event categories for filtering and handling:

- `NoneCategory`: No category.
- `EventCategoryKeyboard`: Keyboard events.
- `EventCategoryMouse`: Mouse events.
- `EventCategoryTimer`: Timer events.
- `EventCategoryFileSys`: File system events.
- `EventCategoryApp`: Application events.
- `EventCategoryEngine`: Engine-specific events.

## Event Class

Base class for all event types.

### Key Methods

- `virtual ~Event()`: Virtual destructor.
- `bool IsHandled() const`: Checks if event was handled.
- `void SetHandled(bool handled = true)`: Marks event as handled/unhandled.
- `virtual EventType GetEventType() const = 0`: Returns event type (pure virtual).
- `virtual const char* GetName() const = 0`: Returns event name (pure virtual).
- `virtual int GetCategoryFlags() const = 0`: Returns category bitflags (pure virtual).
- `bool IsInCategory(EventCategory category) const`: Checks if event is in a given category.
- `virtual std::string ToString() const`: Returns string representation of event (default: name).

### Member Variables

- `bool m_Handled`: Indicates if the event has been handled.

## EventDispatcher Class

Utility for dispatching events to appropriate handlers based on their type (uses templates and `std::function`).

### Key Features

- **Constructor**: `EventDispatcher(Event& event)`: Takes a reference to an Event.
- **Dispatch Method**: `template <typename T> bool Dispatch(EventFn<T> func)`
  - Invokes handler if event is of type `T`.
  - Marks event as handled if handler returns `true`.

## Macros

- `EVENT_CLASS_TYPE(type)`: Adds required type/name methods for derived event classes.
- `EVENT_CLASS_CATEGORY(category)`: Adds category flag method for derived event classes.

## Usage Example

To create a new event type:

```cpp
class KeyPressedEvent : public Event {
public:
    EVENT_CLASS_TYPE(KeyPressed)
    EVENT_CLASS_CATEGORY(EventCategoryKeyboard)
    // Additional methods and members
};
```

To dispatch an event:

```cpp
void OnEvent(Event& e) {
    EventDispatcher dispatcher(e);
    dispatcher.Dispatch<KeyPressedEvent>([](KeyPressedEvent& event) {
        // handle key press
        return true; // marks event as handled
    });
}
```

---

## Summary

This event system provides:

- Strongly-typed, extensible event classes.
- Category-based filtering.
- Simple dispatching mechanism.
- Boilerplate-reducing macros for event types.

Suitable for building modular, type-safe event-driven C++ applications.

# AIAssistant::EventQueue Class Documentation

## Overview

`AIAssistant::EventQueue` is a thread-safe queue for managing pointers to `AIAssistant::Event` objects. It allows events to be safely pushed from multiple threads and consumed by a main thread.

## Key Features

- **Thread-safe**: All operations are guarded with a mutex.
- **Event pointer handling**: Stores and returns `std::shared_ptr<AIAssistant::Event>`.
- **Efficient batch consumption**: Main thread can pop all events at once.

## Public Member Functions

### void Push(EventPtr event)
Adds an event to the queue.

- **Thread-safe**.
- `EventPtr` is a `std::shared_ptr<AIAssistant::Event>`.

### EventPtr Pop()
Removes and returns the front event from the queue.

- Returns `nullptr` if the queue is empty.
- **Thread-safe**.

### std::vector<EventPtr> PopAll()
Removes and returns all events from the queue in a vector.

- Intended for main thread batch processing.
- The queue is empty after this call.
- **Thread-safe**.

### size_t Size()
Returns the current number of events in the queue.

- **Thread-safe**.

## Thread Safety

All member functions lock a mutex to prevent concurrent access issues. The queue can safely be written from multiple threads and read by the main thread.

## Typical Usage

- Worker threads push events using `Push`.
- The main thread periodically fetches and processes all pending events using `PopAll` or processes one by one with `Pop`.
- Use `Size` for queue status or debugging.

## Example

```cpp
AIAssistant::EventQueue queue;

// Worker thread:
queue.Push(std::make_shared<AIAssistant::Event>(...));

// Main thread:
auto events = queue.PopAll();
for (auto& event : events)
{
    // Handle event
}
```

# AIAssistant::KeyEncryption Class Documentation

## Overview

`AIAssistant::KeyEncryption` provides static methods for password-based encryption and decryption of JSON plaintext using AES-256-GCM, with keys derived via PBKDF2-HMAC-SHA256.  
The encrypted output is a binary blob containing metadata and cryptographic parameters necessary for secure storage and retrieval.

## File Format

Each encrypted blob consists of:
- 4-byte magic (`"JKEY"`)
- 1-byte version
- 16-byte salt (PBKDF2)
- 12-byte IV (GCM)
- Ciphertext
- 16-byte GCM authentication tag

## Public Interface

### Encrypt

```cpp
static std::vector<uint8_t> Encrypt(std::string const& plaintext, std::string const& masterPassword);
```

- Encrypts a plaintext JSON string using the provided master password.
- Uses PBKDF2-HMAC-SHA256 key derivation (100,000 iterations, random 16-byte salt).
- Encrypts with AES-256-GCM and stores a 12-byte random IV and 16-byte tag.
- Returns a complete binary blob (header + ciphertext + tag).
- On failure (e.g., random generation or OpenSSL error), logs an error and returns an empty vector.

### Decrypt

```cpp
static std::string Decrypt(std::vector<uint8_t> const& encryptedBlob, std::string const& masterPassword);
```

- Decrypts an encrypted blob with the provided master password.
- Parses and validates the header (magic/version), extracts salt, IV, ciphertext, and tag.
- Derives key with PBKDF2-HMAC-SHA256 using extracted salt.
- Decrypts and authenticates with AES-256-GCM.
- Returns the decrypted plaintext string on success.
- Returns an empty string on failure (wrong password, data tampering, format errors).

## Internal Details

- Constants:
  - MAGIC: `'J','K','E','Y'` (4 bytes)
  - VERSION: `0x01`
  - SALT_SIZE: `16`
  - IV_SIZE: `12`
  - TAG_SIZE: `16`
  - HEADER_SIZE: `33`
  - PBKDF2_ITERATIONS: `100,000`
  - KEY_SIZE: `32` (AES-256)
- Clears sensitive key material from RAM after use.
- Error logging uses `LOG_CORE_ERROR`.

## Example Usage

```cpp
#include "keys/keyEncryption.h"

std::string plaintext = R"({"user":"alice","apikey":"secret"})";
std::string password = "StrongPassword123";

// Encrypt JSON
std::vector<uint8_t> blob = AIAssistant::KeyEncryption::Encrypt(plaintext, password);

// Decrypt JSON
std::string decrypted = AIAssistant::KeyEncryption::Decrypt(blob, password);
```

## Security Notes

- Relies on OpenSSL for all cryptographic operations.
- Never stores plaintext or password in persistent form.
- Output is authenticated: decryption fails for any modified/corrupted data or wrong passwords.
- Always use a strong, unique master password.
- Do not reuse blobs with different data without re-encrypting.

## Dependencies

- [OpenSSL](https://www.openssl.org/)
- Internal logging macro: `LOG_CORE_ERROR`
- C++ Standard Library (`<string>`, `<vector>`, `<cstdint>`, `<cstring>`)

# TerminalLogStreamBuf Class Documentation

## Overview

`TerminalLogStreamBuf` is a custom C++ stream buffer class designed to capture, process, and dispatch log messages to various destinations, including a terminal UI, a file, and a broadcast callback. It is implemented within the `AIAssistant` namespace.

## Purpose

This class is intended for structured and thread-safe logging within applications that require simultaneous log output to:
- A terminal or user interface
- A log file
- Arbitrary recipients via callback (e.g., UI widgets or remote subscribers)

## Key Features

- Inherits from `std::streambuf` to plug into C++ stream systems (e.g., `std::ostream`)
- Removes ANSI escape sequences in log messages before outputting them to log files or callbacks
- Synchronously writes to terminal, file, and broadcast callback
- Thread-safe operations for all mutable states (using mutexes)

## Constructor

```cpp
TerminalLogStreamBuf(TerminalManager* terminalManager, std::shared_ptr<std::ofstream> fileLogger)
```
- `terminalManager`: Pointer to a `TerminalManager`, used to queue log messages to a terminal.
- `fileLogger`: Shared pointer to an `std::ofstream`, used for writing logs to a file.

## Public Methods

### SetLogBroadcastCallback

```cpp
void SetLogBroadcastCallback(std::function<void(std::string const&)> callback)
```
Sets a callback function that will be invoked with each clean log line. Thread-safe.

## Logging Flow

1. **Receiving Log Data:**  
   Data is received via standard stream methods (`overflow`, `xsputn`).

2. **Buffering:**  
   Log data is appended to an internal buffer until newline (`\n`) or other sync conditions occur.

3. **Processing (on sync or newline):**
   - Strips ANSI escape sequences (for clean file and broadcast logging).
   - Enqueues the log line to the terminal (if manager is present).
   - Writes the clean log to the log file (if file logger is set and open).
   - Sends the log line to the callback (if set).

4. **Thread Safety:**  
   All buffer, file, and callback manipulations are protected by mutexes.

## Internal Method(s) of Note

### StripAnsi

Removes ANSI escape sequences from the log line before writing to log file or broadcasting.

### syncLocked

Flushes the current buffer, dispatches log line to terminal, file, and broadcast callback.

## Thread Safety

Mutexes guard:
- The internal buffer (`m_BufferMutex`)
- File log writes (`m_FileMutex`)
- Callback assignment/invocation (`m_CallbackMutex`)

## Intended Usage

- Construct with references to a terminal manager and log file.
- Use as the backing buffer for an `std::ostream` for log streaming.
- Optionally register callbacks for log broadcasting (e.g., for GUI logs or network relay).
- Designed for logging in multi-threaded environments.

## Dependencies

- `TerminalManager` (from `log/terminalManager.h`)
- Standard C++ `<fstream>`, `<functional>`, `<mutex>`, `<streambuf>`, `<string>`

## Example

```cpp
AIAssistant::TerminalLogStreamBuf logBuf(&terminalManager, fileLogger);

std::ostream logStream(&logBuf);

    // Custom broadcast handling
```

## Overview

`TerminalManager` is a C++ class for real-time terminal-based status and log display, designed for use in interactive console applications (e.g., AI assistants). It creates a split terminal UI with log and status windows, supporting UTF-8 input, color highlighting, window resizing, and safe operation across platforms.

## Key Features

- Dynamic log and status panes with adjustable heights and headers.
- UTF-8 sanitization for robust display.
- Color support with theme customization.
- Thread-safe log queueing using mutexes.
- Platform adaption for UNIX and Windows.
- Automatic terminal state restoration on shutdown.
- Resize/reflow of windows when terminal size changes.
- User-supplied callbacks for custom status lines and height.

---

## Class Definition

```cpp
class TerminalManager {
public:
    using StatusLinesCallback = std::function<void(std::vector<std::string>& lines, int maxWidth)>;
    using StatusHeightCallback = std::function<int(int totalRows)>;

    ~TerminalManager();

    void Initialize();
    void Shutdown();

    void RenderPaused(int counter);
```

---

### Rendering

- **void Render()**

- Uses PDCursesMod for cross-platform terminal control.
