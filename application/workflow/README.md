# Workflow Runtime

DAG-based workflow execution engine. Parses JCWF files, resolves dependencies, dispatches tasks in parallel, and tracks execution state.

## Key Files

| File | Purpose |
|------|---------|
| `workflowTypes.h` | Task types, trigger types, run state, TaskDef, WorkflowRun |
| `workflowJsonParser.h/cpp` + `workflowJsonParserDetails.h/cpp` | JCWF JSON parsing into WorkflowDefinition.  Public entry points (`ParseWorkflowJson` / `ParseGlobalJson` / `ParseCanvasJson`), `ParseRootObject`, all 17 chain sub-parsers, and the two `Require*` shape helpers return `[[nodiscard]] std::expected<void, ParserError>` (Sitting 7c) — typed `TypeMismatch` / `MissingField` / `ValueOutOfRange` / `SimdjsonError` codes via `application/workflow/parserError.h`.  Utility helpers `ExtractRawJson` and `ElementToString` stay on the legacy bool shape; chain methods bridge their failures into typed `SimdjsonError` / `TypeMismatch` at the call site.  Parse-time syntactic gate (`IsAcceptedRelativePath` in the Details header) rejects empty / overlength / absolute values in `base_directory`, `working_directory`, `file_inputs`, `file_outputs`, and queue-binding `path` fields — `..` segments are allowed because the shipped `working_directory: "../../queue/<workflow>/<task>"` convention requires them; layered with the consumer-side `ConfineUnderProjectRoot` gate (use sites listed in `application/file/README.md`).  Element-count caps in `WorkflowParserLimits` namespace bound heap pressure from a hostile JCWF (`kMaxTasks=1000`, `kMaxTriggers=100`, `kMaxDataflows=10000`, `kMaxFilters=100`, `kMaxFileInputsPerTask=1000`, `kMaxQueueFilesPerSection=1000`, `kMaxInlineContentBytes=1MB`, `kMaxRetryAttempts=100`, `kMaxBackoffMs=1h`, `kMaxTimeoutMs=7d`).  `timeout_ms` and `retries.{max_attempts,backoff_ms}` are validated as non-negative AND under their cap before casting to unsigned, closing the negative-wrap-to-near-INFINITY DoS vector.  `ParseRootObject` takes `simdjson::ondemand::object&` (matches every other Parse* helper); never copy an ondemand object — it's a shallow copy of pointers into the document arena. |
| `workflowRegistry.h/cpp` | Loads and indexes .jcwf containers from the workflows folder. Single `mutable std::mutex m_Mutex` serializes every public method that touches `m_Workflows` / `m_BrokenWorkflows` (REST handlers, runtime-tick `GetWorkflow`, file-watcher reload). Private `LoadContainer` / `LoadContainerSubWorkflows` assume the lock is held by the public-method caller. Path-bearing operations (`SaveOrUpdateWorkflowFromJson` write, `RemoveWorkflow` delete) are gated through `application/file/pathConfinement.h::ConfineUnderProjectRoot`; the multi-step file/registry work in `SaveOrUpdateWorkflowFromJson` is wrapped in try/catch with the m_Workflows insert as the LAST step inside the try, so a thrown filesystem exception cannot leave the registry holding a half-built definition.  `RemoveWorkflow` returns `[[nodiscard]] std::expected<void, RegistryError>` — typed `NotFound` / `PathRefused` / `IoError` codes via `application/workflow/registryError.h`.  `ExtractProviderFromParams` expands `{{defaults.X.Y}}` template references against the workflow's `m_DefaultsJson` at load time (via `templateEngine.h::BuildDefaultsMap` + `ExpandWithDefaults`) so `m_RequiredAiProviders` carries resolved interface names — the dashboard's `interface_names` UI + the prereq check at `workflowRuntimeManager.cpp` both see the real provider, not the raw template string. |
| `workflowRuntimeManager.h/cpp` | Run lifecycle, task dispatch, dependency resolution, cancellation. `Update()` holds `m_Mutex` for the entire tick (drain + propagate + tick + finalize + erase) so REST snapshot readers cannot tear-read mutating run state; external calls (`AiRequestPool::CancelRequestsForRun`, `FireCompletionCallback`, `RunTerminalObserver`) are deferred to a `postTickActions` vector and fired AFTER the lock is released. Worker-thread lambdas in `TickActiveRun` capture `WorkflowDefinition` by value. Path-bearing operations (`CleanWorkflow`'s deletes) are gated through `application/file/pathConfinement.h`. The completion-callback `callbackUrl` is gated through `IsCallbackUrlAllowed` (https-only + DNS-resolved internal-IP rejection + TLS verify) before any payload is built. See `doc/architecture.md` "Key Design Decisions" rows for rationale. |
| `workflowValidator.h/cpp` | JCWF validation (structure, references, working_directory) |
| `workflowFileIndex.h/cpp` | File freshness tracking (SHA-256 manifests).  `FindByRelativePath` enforces `lexically_relative(m_RootDirectory)` containment so a hostile relative path can't enumerate files outside the workflow tree. |
| `jcwfContainer.h/cpp` | JCWF zip container read/write.  `Extract` runs a two-pass design: a validation pass (NO disk I/O) walks every entry first; any rejection aborts the whole extraction before the first byte hits disk.  Three layers of Zip-Slip defense in `ValidateEntryName` + `IsSymlinkEntry` + `ValidateContainment` (file-local helpers): rejects absolute / `..`-laced / empty-segment / NUL-containing entry names (both `/` and `\` separators tokenised), rejects entries whose Unix `external_attr` upper bits match `S_IFLNK` (`0xA0000000` mask) so a symlink entry can't be staged for follow-up traversal, and `weakly_canonical(destPath)` (not `canonical`, because the entry doesn't exist on disk yet) + lexicographic prefix check against `weakly_canonical(targetDir)` confirms the resolved destination stays under the resolved target after ancestor-symlink resolution.  Fail-closed `LOG_APP_ERROR` carries `container='{}' entry='{}' reason='{}'` literals.  `weakly_canonical` is the right tool here because the entry doesn't exist on disk yet — `canonical` requires the path to exist; `lexically_normal` doesn't resolve symlinks. |
| `triggerEngine.h/cpp` | Cron, file-watch, webhook, S3/OneDrive/email/Azure-Blob/GCS polling, and manual triggers. `Tick()` runs single-threaded from the main loop; the email-poll loop drops `m_Mutex` for IMAP I/O and re-acquires it for the watermark update — re-acquire uses **identity-based lookup** (`workflowId` + `triggerId`) rather than the pre-collected vector index, so a concurrent `ClearWorkflowTriggers` between lock release and re-acquire cannot misroute the watermark to a different trigger. `NormalizePath` routes through `application/file/pathConfinement.h::ConfineUnderProjectRoot` for both file-watch trigger registration AND the FileWatcher event side, so an embedded `..` in an event path cannot prefix-match a watched directory. Per JC_Workflow_Specification §3.2.2, file_watch paths are project-root-relative — the spec is the design cover for the canonical-form normalization. |
| `workflowTriggerBinder.h/cpp` | Binds parsed trigger definitions to TriggerEngine.  Webhook triggers require a non-empty `params.secret` field — `ParseWebhookParams` fails closed on every failure mode (empty params JSON, parse error, non-object root, missing/empty `secret`) with an ERROR log naming the cause; the caller breaks out of the case and skips registration entirely.  Defense in depth on top of TriggerEngine's own empty-secret refusal. |
| `taskPathResolver.h/cpp` | Resolves working directories and file paths per task.  **Pure pass-through resolver** — does NOT enforce containment.  Containment is the **caller's** responsibility: pass any external path through `application/file/pathConfinement.h::ConfineUnderProjectRoot` (or scope-tighter `lexically_relative(<base>)` containment) BEFORE handing the resolved value to a filesystem-touching API.  See header trust-model block + the shared pathConfinement README's use-site list. |
| `taskExecutorRegistry.h/cpp` | Maps TaskType enum to ITaskExecutor implementations.  `MaterializeFiles` enforces `lexically_relative(taskWorkingDirectoryPath)` containment on the JCWF-authored `targetFilename` so a hostile materialise entry can't escape the task working directory via `..`-laced names. |
| `aiRequestPool.h/cpp` | Parallel AI API dispatch pool. Computes the size-aware curl `CURLOPT_TIMEOUT_MS` budget per request, plumbs `QuotaKey` to the dispatcher's adaptive controller, fires cascade-cancellation when a run terminates (`CancelRequestsForRun`).  Forwards the resolved interface's `is_mock` + `fixture_path` onto `QueryData` so the dispatcher can route mocked requests through `MockTransport` (transparent to this pool — mock-ness is a transport-layer concern).  For AWS SigV4 paths, `ResolveAwsCredentialSnapshot` takes a deep-copy `shared_ptr<AwsCredential const>` snapshot under KeyManager's lock (see `engine/keys.md` "Snapshot pattern for deferred dispatch") and threads it into `QueryData::m_AwsCredential`; SigV4 signing reads typed credential fields directly instead of stringy `m_Params` reinjection.  Inflight counter (`m_DirectDispatchInflight`) uses a per-submission `shared_ptr<atomic_flag>` captured into the curlCallback to ensure exactly-once decrement — both the schema-retry decrement-then-recurse path and the end-of-callback path go through the flag. Every filesystem-touching surface (`WriteTextFile` write, `OnOutputFileCreated` read, `RegisterPendingWorkflowTask` insert + `Submit` lookup + cancel-key build, `OnRequestFailed` lookup) routes through `application/file/pathConfinement.h::ConfineUnderProjectRoot` for a single canonical form across insert/lookup/cancel matching.  `WriteTextFile` routes the confined path through `EngineCore::AtomicWriteFile` (see `engine/auxiliary/auxiliary.md`) so a SIGKILL or disk-full mid-write leaves the previous version of the final file intact instead of a truncated partial that `OnOutputFileCreated` would parse as malformed. `OnOutputFileCreated` enforces a 10 MB output-file cap to bound RAM growth from a hostile `expectedOutputPath`.  Public bool-returning APIs (`Submit`, `OnOutputFileCreated`, `OnRequestFailed`, `TryConsumeResult`, `TryPopCompletion`, `WaitForCompletion`) are `[[nodiscard]]`. |
| `aiCallTaskExecutor.h/cpp` | AI call task execution (queue file assembly, API dispatch).  Queue-binding source paths (CNTX + PROB) route through `application/file/pathConfinement.h::ConfineUnderProjectRoot` before any open — same project-root-wide gate as every other ai_call/queue site, so a documented JCWF cross-task data-flow path (e.g. reading a sibling task's output via `../../../workflows/<id>/<other_task>/output.json`) succeeds while absolute / out-of-tree / symlink-escape inputs are refused.  `WriteTextFile` routes through `EngineCore::AtomicWriteFile` so a SIGKILL or disk-full mid-write never leaves a truncated partial.  `ReadTextFile` enforces a 100 MB size cap (defends against `/dev/zero`, fifos, runaway logs). `ExpandCntxFileGlobs` caps glob matches at 10000.  `ConvertWithMarkitdown` uses an allowlist (`[A-Za-z0-9/._\-+=:]`) on input paths before constructing the `popen` shell command — replaces a too-narrow blocklist that missed `;`, `\|`, `&`, `(`, `)`, `<`, `>`, etc.  Provider-sidecar JSON (`PROV_provider.json`) routes every string field through `JsonHelper::EscapeJsonString`; `temperature` is parsed as a finite double in `[0,2]` before being emitted as a JSON number — closes a JSON-injection vector.  When the resolved interface has `is_mock: true`, PROV carries `"mocked": true` + `"fixture_path"` so post-mortem tooling distinguishes mock dispatches from live ones.  `BuildDefaultsMap` logs at WARN on simdjson exceptions instead of swallowing silently. |
| `aiTranscript.h/cpp` | Per-PROB transcript writer (`<prob>.transcript.json`).  Concurrent writers serialised via a single in-process mutex; read-modify-write routes through `EngineCore::AtomicWriteFile` so a crash mid-write never leaves a truncated file.  `MessageRoleToString`, `AiReply::Kind` switch, and `AiError::Kind` switch are exhaustive (`-Wswitch` catches missing variants).  Provider error messages are `SanitizeUtf8` + `TruncateUtf8Safe(1024)`-bounded before disk write.  `Kind::Structured` payloads round-trip through simdjson DOM (canonical re-emission) so a malformed `m_StructuredJson` cannot corrupt the surrounding transcript array.  `ReadFile` enforces a 64 MB transcript-size cap.  `AppendRequest`/`AppendResponse` are `[[nodiscard]]` so the bool return is mechanically surfaced at every call site. |
| `scriptCatalog.h/cpp` | Walks `scripts/` for `.sh` / `.py` / `.ps1` files.  Symlinks skipped; canonical paths confined under the canonical scripts root (defense against symlinks pointing outside the tree).  Catalog entries capped at 10000.  `Refresh` builds the new entry vector OUTSIDE the lock and swaps under-lock at the end so concurrent `List` / `GetByPath` callers aren't blocked for the full I/O duration. |
| `filter/filterManifest.h/cpp` | Per-filter cache manifest reader/writer.  `ManifestPath` validates the filterId (allowlist `[A-Za-z0-9._\-]`, no `..`, no leading dot) and routes through `ConfineUnderProjectRoot` — closes the path-traversal-via-filterId vector.  `ReadManifest` caps file size at 16 MB and items at 1M; `WriteManifest` routes through `EngineCore::AtomicWriteFile`.  `ComputeQueryHash` is OpenSSL SHA-256-only (the std::hash fallback was removed as predictable / collision-prone).  `FileMtimeString` uses C++20 `std::chrono::file_clock::to_sys` (replaces a racy clock-offset approximation). |
| `adhocWorkflowManager.h/cpp` | Stages, executes, and reaps adhoc JCWFs submitted via `POST /api/workflows/run-adhoc`. Per-user folder layout under `_adhoc/<user_slug>/<timestamp>_<counter>_del-<delete-at>/`; the folder name encodes the delete-at instant so the reaper is stateless and restart-safe. Stage enforces a 4 MB JCWF size cap, calls `WorkflowRegistry::SaveOrUpdateWorkflowFromJson` for the canvas write (which applies project-root containment), and rolls the partial folder back on every post-create-directories failure. `WriteMeta` is `[[nodiscard]] bool` so a failed meta.json write triggers folder rollback rather than leaving an un-attributable run on disk. Reaper thread uses a `condition_variable` for fast shutdown; Start/Stop are serialized by `m_ReaperLifecycleMutex` so concurrent calls cannot race the std::thread member. See `doc/cyber security.md` "Adhoc workflow submission" for the threat model. |

The adaptive rate-limit controller (`RateLimitController`) and per-provider strategy (`IRateLimitStrategy`) live in `engine/curlWrapper/` — see `engine/curlWrapper/curlWrapper.md` §15 and `doc/architecture.md` "Rate-limit + concurrency control" for the design.

## Task Executors

| File | Task Type | Description |
|------|-----------|-------------|
| `shellTaskExecutor` | `shell` | Shell command execution via subprocess.  `command` MUST resolve under `<projectRoot>/scripts/` (gated via `application/file/pathConfinement.h::ConfineUnderProjectRoot` + explicit `lexically_relative` containment).  `args[]` are **always** single-quoted before joining into the `sh -c` string — globbing, variable expansion, and command substitution are neutralised regardless of arg content.  `IsSafeArgument` extends the blocklist to `; & \| > < ' " \` $ ( ) \\` as defense in depth.  popen FILE* uses `PipeCloser` RAII so a read-loop exception doesn't leak the child process.  `s_WindowsShell` is `std::atomic<WindowsShell>` for concurrent Probe/Get safety.  Per-task unique `.ja_stderr_<pid>_<counter>.tmp` filename eliminates cross-task stderr-capture races and symlink-bait predictability.  `JARVIS_PORT` injected into the child env reads from `Core::g_Core->GetConfig().m_Port` (8443 fallback). |
| `pythonTaskExecutor` | `python` | Python script execution via PythonEnginePool.  `taskDefinition.m_FileInputs[i]` paths are gated through `ConfineUnderProjectRoot` in `ValidateFileInputsExist` before the existence check, so a hostile JCWF can't surface out-of-tree files into the Python context.  The `taskWorkingDirectory` containment in `pythonEngine.cpp::SetupSubInterpreter` / `ExecuteWorkflowTaskOnWorker` covers the working-directory side of the same gate. |
| `aiCallTaskExecutor` | `ai_call` | AI API calls with queue file assembly |
| `internalTaskExecutor` | `internal` | Built-in operations (zip, copy, etc.) |
| `subWorkflowTaskExecutor` | `sub_workflow` | Nested workflow execution.  `taskDefinition.m_WorkflowFile` is gated through `ConfineUnderProjectRoot` before registry lookup — a hostile JCWF can't reference a workflow file outside the project tree. |

Cloud task executors are in `application/cloud/` — see `application/cloud/README.md`.
